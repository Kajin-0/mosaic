# Mosaic Preliminary Architecture

## Architectural objective

Keep product delivery, persistent data, and scientific inference independently testable while preserving a single source of truth for interfaces and experimental provenance.

```text
+------------------------------+
| apps/mobile                  |
| React Native / Expo / TS     |
+--------------+---------------+
               |
               | authenticated HTTPS
               v
+------------------------------+
| services/engine              |
| Python / FastAPI             |
| application + science API    |
+------+----------------+------+
       |                |
       |                | experiment/generation request
       v                v
+-------------+   +-----------------------+
| Supabase /  |   | Synthetic generator   |
| PostgreSQL  |   | adapter (later)       |
+-------------+   +-----------------------+

Shared API/data definitions live under packages/contracts where appropriate.
```

## Repository boundaries

### `apps/mobile`
Owns presentation, local interaction state, navigation, client-side validation, secure authentication session handling, and network calls.

Must not own matching equations, psychometric scoring, Bayesian inference, or final recommendation logic.

### `services/engine`
Owns server-side application orchestration and scientific algorithms. Starts with deterministic placeholders behind stable endpoints and evolves without requiring client rewrites.

### `supabase`
Owns database migrations, local Supabase configuration, seed data, and database policy definitions. The database schema is source-controlled; hosted dashboard state is not the source of truth.

### `packages/contracts`
Owns reusable non-secret TypeScript-facing contracts and generated/static API types needed by the mobile client. The canonical HTTP API schema remains the server's versioned contract.

### `docs`
Owns architecture decisions, scientific protocols, experiment definitions, and project handoff material.

## Core invariants

1. **Server-authoritative science** — scientific predictions and experimental policies are generated by the engine, not duplicated in the mobile client.
2. **Raw evidence is immutable** — raw questionnaire/calibration responses are not overwritten by later model interpretations.
3. **Predictions are versioned** — every scientifically meaningful prediction records the model/policy version and evidence time.
4. **Schema is migration-controlled** — production database changes originate from versioned migrations.
5. **Experiments are reproducible** — responses trace to immutable stimulus/instrument IDs and enough provenance to audit the presentation.
6. **Client credentials are least-privilege** — privileged server/service credentials never enter the mobile bundle.
7. **Idempotent writes where retry is expected** — response/event ingestion must tolerate mobile-network retries.
8. **No engagement objective leaks into science contracts** — infrastructure should record scientific/product events without defining time-in-app or swipe volume as optimization targets.

## Initial API boundary

Version all product/science endpoints under `/v1` once they can affect persisted user state or model interpretation.

Initial skeleton:

```text
GET  /health
GET  /version
POST /v1/calibration/next
POST /v1/calibration/response
POST /v1/matches/rank
```

The first implementations are deterministic mocks. This is intentional: API and persistence behavior must become testable before model sophistication is introduced.

## Data identity separation

Prefer pseudonymous internal identifiers at the engine boundary. Authentication and contact identity belong to the account/auth layer; scientific services should receive only the identity information required to perform the computation.

## Model provenance

Every persisted model output should support fields equivalent to:

```text
model_name
model_version
policy_version
created_at
evidence_cutoff
input_schema_version
output_schema_version
```

Historical outputs are append-only where scientifically relevant.

## Environments

At minimum:

```text
local
preview/staging
production
```

Local development must be reconstructable from repository state plus documented secret/environment variables.

## Initial deployment philosophy

Do not optimize infrastructure for theoretical scale before the vertical slice exists. Prefer managed services and containers with explicit interfaces. Components may be split later if measured load, security isolation, or independent deployment cadence justifies it.
