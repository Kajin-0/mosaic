# Phase 7 Operational Hardening Protocol

## Purpose

Phase 7 converts the infrastructure accumulated in Phases 1–6 into one operationally testable system. The protocol does not add matchmaking science. It asks whether the existing application, security boundaries, experimental ledgers, and replay guarantees remain observable, recoverable, and review-blocking under one repository-wide gate.

## Preconditions

A clean runner must have:

- Docker;
- Node.js 22.16.0;
- Python 3.13;
- pinned `uv` 0.12.4;
- the committed npm and Python lockfiles; and
- no externally provisioned Mosaic secrets.

Supabase credentials used by the protocol are generated by the local Supabase runtime and exist only for the runner lifetime.

## Protocol A — source and dependency integrity

1. Check out the full pull-request history.
2. Install Python and JavaScript dependency graphs from committed lockfiles.
3. Scan the pull-request history for secrets.
4. Run Python Ruff lint/format checks.
5. Run mypy over `services/engine/src/mosaic_engine`.
6. Run all engine pytest tests.
7. Regenerate OpenAPI from FastAPI.
8. Regenerate TypeScript API declarations from OpenAPI.
9. Validate the explicit contract surface.
10. Run mobile typecheck/lint/tests.
11. At the end of the workflow, require zero diff in dependency locks and generated contract artifacts.

### Failure meaning

A failure is not automatically a build nuisance. In particular:

- a mypy failure can reveal a mismatch between an implementation value and the persisted/wire type contract;
- generated-contract drift means the committed API evidence does not describe the running server;
- lockfile drift means CI did not execute the dependency graph represented by the repository; and
- a secret finding requires credential investigation/rotation if the value is genuine.

## Protocol B — local database and authorization reconstruction

1. Start the pinned local Supabase stack.
2. Rebuild the database entirely from migrations and deterministic seed data.
3. Export the local publishable/anonymous and service-role runtime values into runner-scoped environment variables.
4. Execute the Phase 2 two-user authentication/RLS protocol.
5. Require owner access and cross-user isolation to remain intact.

No checked-in credential is involved.

## Protocol C — mobile/runtime reconstruction

1. Build/typecheck/lint/test the Expo client.
2. Export Android, iOS, and web bundles.
3. Start the real FastAPI/Uvicorn process against the reconstructed local database.
4. Require `/health` to become reachable before proceeding.

## Protocol D — inherited experimental replay

Against the same process and database, execute in order:

1. Phase 4 ten-trial calibration replay.
2. Phase 5 twenty-item measurement replay and rescoring.
3. Phase 6 twenty-pair synthetic-calibration replay.
4. Phase 6 completed-session provenance immutability probes.

The P7 gate must not replace these with mocks or abbreviated row-count checks. Their existing replay semantics remain the regression oracle.

## Protocol E — request observability

Unit/integration tests require that request events contain:

- bounded request ID;
- method/path/status;
- elapsed milliseconds;
- engine/API/contract versions;
- route-relevant policy/model version when applicable; and
- stable one-way `subject_ref` after science authentication.

The raw authentication user ID and raw science UUID are not emitted as log identity fields.

Unsafe externally supplied request IDs are replaced rather than reflected verbatim.

An unexpected exception must produce a `request_failed` event with status 500 and `error_type` before the exception propagates.

## Protocol F — internal-alpha latency regression budget

After two warm-up requests per operation, collect 20 sequential local samples for each:

1. `GET /health`
2. `GET /version`
3. `POST /v1/matches/rank`
4. repeated pending/cached `POST /v1/calibration/next`
5. repeated pending/cached `POST /v1/measurement/next`

For each operation:

```text
p95 < 500 ms
```

The aggregate 100-sample p95 must also satisfy the same threshold.

Every measured response must return the supplied safe request ID in `x-request-id`.

### Non-claim

This is a local CI regression threshold. It does not establish hosted production capacity, concurrency behavior, geographic network latency, database-scale performance, or image-generation latency.

## Protocol G — destructive detached science-evidence recovery

The preceding P4–P6 replays populate a complete non-empty science graph.

### Backup

Read and canonically order:

- `science_subjects(subject_id, created_at)`;
- Phase 4 sessions/trials/responses;
- Phase 5 sessions/presentations/responses/score runs;
- Phase 6 sessions/specifications/assets/QC/pairs/responses.

Do **not** include `science_subjects.user_id` in the detached recovery representation.

Calculate:

```text
backup_fingerprint = SHA256(canonical_backup_json)
```

Persist the runner-local backup file with restrictive permissions.

### Destruction

Run a full local database reset from migrations and seed data.

Require the critical science evidence tables to be empty after reset. If evidence survives unexpectedly, the drill is invalid because it did not prove restoration.

### Restore

Restore the detached graph in foreign-key dependency order. Restored science subjects have `user_id = NULL` unless a separate privileged identity-relink procedure is intentionally executed later.

### Verification

Read the entire detached graph again and require:

```text
SHA256(canonical_restored_json) == backup_fingerprint
```

Also require exact equality of every backed-up table row count.

Then rerun the Phase 2 RLS test against the reconstructed database so recovery cannot silently weaken authorization semantics.

## Phase 7 exit criterion

The consolidated, read-only workflow must pass the complete protocol on one exact pull-request head with no CI-authored source changes.

Only after that proof may the phase-specific P1–P6 workflows be retired. The consolidated gate must then pass again on the workflow-retirement head before Phase 7 is considered complete.
